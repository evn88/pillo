## ADDED Requirements

### Requirement: Recoverable startup

Приложение MUST различать загрузку, готовность и восстановимую ошибку открытия локальных данных; отказ MUST сохранять исходную БД и давать понятную повторную попытку.

#### Scenario: Ошибка чтения при запуске

- **WHEN** открытие или декодирование существующей БД завершается ошибкой
- **THEN** пользователь видит причину в безопасной форме и действие повтора вместо бесконечного spinner
- **AND** приложение не подменяет существующие данные пустым snapshot и не планирует события из непроверенных данных

#### Scenario: Восстановление после временного отказа

- **WHEN** причина временного отказа устранена и пользователь повторяет открытие
- **THEN** приложение загружает прежние данные без дубликатов и закрывает неиспользуемые handles

### Requirement: Reliable commands

Изменения MUST выполняться последовательно относительно последнего подтверждённого состояния. Результат команды MUST различать валидацию, отказ записи и успешную запись с отдельной проблемой уведомлений. Повтор одного намерения MUST быть идемпотентным.

#### Scenario: Две команды до завершения сохранения

- **WHEN** пользователь отправляет два разных допустимых изменения до завершения первой записи
- **THEN** оба изменения последовательно сохраняются и присутствуют после повторного открытия БД
- **AND** отказ одной команды не откатывает последующую успешную команду

#### Scenario: Ошибка сохранения формы

- **WHEN** SQLite отказывает при сохранении новой записи
- **THEN** форма остаётся открытой с исходным вводом, ошибкой и возможностью повтора
- **AND** UI не показывает запись как подтверждённую и не обновляет системный план по несохранённым данным

#### Scenario: Повтор сохранения и поздняя ошибка уведомлений

- **WHEN** данные уже сохранены, но обновление уведомлений не завершилось
- **THEN** UI сообщает отдельно о необходимости восстановления уведомлений
- **AND** повтор одного command ID не создаёт второе правило, препарат или ручной приём

#### Scenario: Свайп после последующих изменений

- **WHEN** после создания карточки A пользователь добавил/изменил B и удаляет A полным свайпом с подтверждением
- **THEN** удаление применяется к актуальному состоянию, сохраняя B и все его изменения
- **AND** отмена подтверждения ничего не меняет

### Requirement: Validated inputs

Приложение MUST использовать единые domain-правила проверки на границах UI, команд и сохранённых данных. Неверная доза MUST NOT заменяться значением по умолчанию или clamp. Количество MUST быть конечным и представимым в выбранном формате точности.

#### Scenario: Десятичная запятая

- **WHEN** пользователь вводит `0,5` или `0.5` как дозу
- **THEN** приложение сохраняет количество 0.5 и показывает его без изменения значения

#### Scenario: Быстрые дробные дозы

- **WHEN** пользователь выбирает ¼ или ½ в расписании, ручном приёме либо редакторе фактической дозы
- **THEN** единый валидатор получает соответственно 0.25 или 0.5 без округления и скрытой подмены

#### Scenario: Неприемлемое числовое значение

- **WHEN** пользователь вводит пустую, нулевую или отрицательную дозу, Infinity, NaN, смешанный разделитель или значение за пределами поддерживаемой точности
- **THEN** запись блокируется с ошибкой соответствующего поля
- **AND** doseUnits не становится 1, 0.25 или null автоматически

#### Scenario: Неверное правило

- **WHEN** команда содержит `99:99`, невозможную дату, лишний сегмент даты, endDate раньше startDate, неверные дни недели либо отсутствующий medicationId
- **THEN** команда отклоняется до сохранения, материализации и scheduling

#### Scenario: Неактивный препарат

- **WHEN** препарат неактивен
- **THEN** новый план и напоминания для него не создаются, а UI объясняет недоступность соответствующего действия

### Requirement: Reversible inventory

Приложение MUST сохранять реально применённое изменение остатка отдельно от зарегистрированной дозы. Отмена MUST обращать только соответствующий stock effect без потери независимых операций и без выдумывания legacy-данных.

#### Scenario: Доза превышает учётный запас

- **WHEN** при остатке 0.5 регистрируется фактический приём 1, затем он отменяется
- **THEN** запись приёма сохраняет дозу 1, временный остаток равен 0, а итоговый после отмены равен 0.5
- **AND** расхождение учётного запаса показано пользователю

#### Scenario: Независимое пополнение между приёмом и отменой

- **WHEN** после приёма добавлена упаковка и затем отменён исходный приём
- **THEN** возвращается только применённое списание и добавленная упаковка остаётся учтённой
- **AND** повтор того же статуса не изменяет остаток или фактическое время

#### Scenario: Неизвестное списание старой записи

- **WHEN** отменяется перенесённый из v1 факт без доказанного stock effect
- **THEN** приложение запрашивает явное решение по корректировке запаса и не возвращает автоматически полную дозу

#### Scenario: Отмена ручного факта

- **WHEN** пользователь отменяет ручную отметку
- **THEN** её известный stock effect обращается и ручной факт удаляется или отмечается отменённым
- **AND** новый плановый PENDING из ручной записи не возникает

### Requirement: Calendar lifecycle

Приложение MUST использовать единый локальный календарный контекст и идемпотентно восстанавливать актуальный план при старте, foreground, смене дня и timezone. Неизвестные периоды MUST отличаться от дней без плана.

#### Scenario: Полночь при открытом приложении

- **WHEN** активное приложение проходит местную полночь
- **THEN** дата, счётчики и приёмы «Сегодня» обновляются без remount и перезапуска

#### Scenario: Возврат после нескольких дней

- **WHEN** пользователь возвращается из фона через несколько дней
- **THEN** текущие приёмы восстановлены без дублей
- **AND** прошлые ожидавшиеся события восстановлены только в пределах доказанного покрытия правил; остальные периоды явно неизвестны

#### Scenario: Путешествие и DST

- **WHEN** timezone изменилась либо местное время правила попадает в весенний разрыв или осеннее повторение
- **THEN** UI и системный план следуют одной политике из design.md: новое местное время, перенос вперёд для разрыва и один первый instant для повторения
- **AND** уже зарегистрированные факты не переписываются

### Requirement: Schedule reconciliation

Изменение расписания MUST обновлять ещё не наступившие PENDING и соответствующие напоминания, сохраняя завершённые и уже наступившие факты.

#### Scenario: Изменение времени, дозы и препарата

- **WHEN** будущий PENDING r1 сегодня изменяется с m1/09:00/1 на m2/10:00/2
- **THEN** экран и желаемое уведомление содержат m2/10:00/2
- **AND** старый ожидающий экземпляр не остаётся параллельно новому

#### Scenario: Отключение дня или правила

- **WHEN** день исключён либо правило отключено
- **THEN** его ещё не наступившие PENDING и напоминания удаляются
- **AND** прошлое и уже зарегистрированные статусы/остатки сохраняются

#### Scenario: Изменение после завершённого occurrence

- **WHEN** для пары ruleId/localDate уже есть завершённый факт
- **THEN** правка правила не создаёт второй приём той же пары и не меняет дозу старого факта

### Requirement: Historical integrity

История MUST сохранять контекст фактов независимо от текущего правила/названия лекарства и отличать сознательный пропуск, отсутствие отметки и неизвестные данные. Уничтожение фактов MUST требовать отдельного точного подтверждения.

#### Scenario: Удаление правила с историей

- **WHEN** пользователь подтверждает удаление будущего расписания
- **THEN** прошлые TAKEN/SKIPPED/неотмеченные события и текущий запас остаются

#### Scenario: Переименование препарата

- **WHEN** название или дозировка препарата изменены после нового зарегистрированного факта
- **THEN** история сохраняет контекст на момент факта и показывает плановое/фактическое время
- **AND** legacy-контекст без достоверного прошлого отмечен как восстановленный из текущих данных

#### Scenario: Приём не отмечен

- **WHEN** ожидавшийся приём не получил действия пользователя
- **THEN** он доступен в истории как неотмеченный, не считается автоматически сознательно пропущенным и не исчезает из-за фильтра PENDING

#### Scenario: Быстрый ручной приём

- **WHEN** пользователь выбирает «Принять сейчас»
- **THEN** количество явно показано/выбрано до регистрации; скрытая безусловная доза 1 не применяется

#### Scenario: Быстрое подтверждение плановой дозы

- **WHEN** ожидающий приём содержит дозу расписания и пользователь нажимает основное действие
- **THEN** одной идемпотентной командой сохраняются TAKEN, эта доза и соответствующий stock effect
- **AND** подпись действия заранее показывает сохраняемую дозу

#### Scenario: Фактическая доза отличается от расписания

- **WHEN** пользователь открывает явное действие изменения дозы и подтверждает другое положительное количество
- **THEN** фактическая доза, статус и stock effect текущего приёма сохраняются атомарно
- **AND** правило расписания, будущие приёмы и их плановая доза не меняются
- **AND** изменение доступно без обязательного свайпа или долгого нажатия

### Requirement: Honest notification coverage

Приложение MUST планировать уведомления в пределах доказанных возможностей ОС и явно показывать фактическое покрытие. Создание ограниченного числа событий MUST NOT объявляться полным покрытием более длинного периода.

#### Scenario: Плотное расписание без запуска

- **WHEN** задано 10 ежедневных событий и приложение не открывается 35 дней без сети
- **THEN** поддержанный автономный режим обеспечивает заявленный план в пределах системных разрешений
- **OR** до включения ограниченного режима пользователю явно сообщена дата окончания покрытия и необходимость его продления
- **AND** факт проверки/ограничения записан отдельно для iOS и Android

#### Scenario: Ограниченный курс и повторения

- **WHEN** выбран повторяющийся системный trigger для курса с startDate/endDate или исключением одного приёма
- **THEN** доказано отсутствие срабатываний вне курса и на исключённый occurrence при сохранении последующих событий
- **AND** если такой контракт не поддержан, используется другая стратегия или явно ограниченный режим

### Requirement: Recoverable notification projection

Системный план MUST строиться из сохранённых данных с учётом статусов приёмов и восстанавливаться после сбоя. Сверка MUST быть последовательной, идемпотентной и привязанной к ревизии.

#### Scenario: Сбой создания части уведомлений

- **WHEN** OS API завершается ошибкой на третьем событии
- **THEN** состояние синхронизации остаётся незавершённым и видимым, данные не откатываются
- **AND** следующая сверка после перезапуска восстанавливает актуальный набор без дублей и устаревших событий

#### Scenario: Новая правка во время сверки

- **WHEN** во время scheduling пользователь меняет или удаляет правило
- **THEN** завершение старой ревизии не помечает новую выполненной и конечный системный план соответствует последним сохранённым данным

#### Scenario: Ранняя отметка приёма и отмена

- **WHEN** будущий occurrence отмечен TAKEN или SKIPPED
- **THEN** отменяется только его напоминание и сохраняются будущие дни
- **AND** undo до наступления времени восстанавливает актуальное напоминание

#### Scenario: Изменение темы

- **WHEN** меняется только тема приложения
- **THEN** существующая очередь уведомлений не отменяется и не пересоздаётся

### Requirement: Effective notification permissions

Приложение MUST различать пользовательское включение, разрешение ОС, доступность канала, точность scheduling и результат сверки. Разрешение POST_NOTIFICATIONS MUST NOT считаться доказательством exact-alarm access.

#### Scenario: Отказ или отзыв разрешения

- **WHEN** пользователь отклоняет разрешение либо отзывает его в ОС
- **THEN** интерфейс показывает недоступность доставки и понятное действие для восстановления
- **AND** возврат из системных настроек обновляет состояние без перезапуска приложения

#### Scenario: Provisional и неточное время

- **WHEN** iOS разрешает только тихую доставку либо Android не разрешает точное scheduling
- **THEN** UI показывает фактический режим и не обещает обычную/точную доставку

### Requirement: Notification navigation

Приложение MUST обрабатывать cold/warm notification response после готовности данных, используя валидированный occurrence ID и безопасный fallback.

#### Scenario: Открытие нужного приёма

- **WHEN** пользователь нажимает уведомление существующего occurrence при закрытом или открытом приложении
- **THEN** после bootstrap показан соответствующий приём/контекст без автоматической отметки TAKEN

#### Scenario: Устаревший или повреждённый payload

- **WHEN** ссылка указывает на удалённый приём либо имеет некорректный payload
- **THEN** приложение показывает нейтральный доступный экран и не меняет данные

### Requirement: Safe persistence and migration

Repository MUST проверять формат, версию и инварианты данных, использовать монотонные атомарные миграции и управлять жизненным циклом соединений. Отказ MUST сохранять исходные данные и не давать ложного успеха записи.

#### Scenario: Повреждённая или более новая база

- **WHEN** payload невалиден, отсутствует обязательная строка существующей БД или версия выше поддерживаемой
- **THEN** приложение не записывает emptySnapshot, не понижает версию и предлагает восстановление

#### Scenario: Нулевая запись

- **WHEN** UPDATE неожиданно изменяет ноль строк
- **THEN** команда возвращает ошибку целостности/сохранения, а не успешный результат

#### Scenario: Обновление с v1 и прерывание

- **WHEN** установленная v1 с существующей историей обновляется и миграция завершается успешно либо прерывается
- **THEN** успешный результат сохраняет ID/статусы/остатки/settings, а прерывание позволяет открыть прежние данные или согласованную recovery-копию
- **AND** неизвестные stock effects не восстанавливаются выдуманными значениями

#### Scenario: Повторное монтирование владельца

- **WHEN** владелец repository размонтирован во время bootstrap или после ошибки
- **THEN** неиспользуемые handles закрываются, незавершённый bootstrap не публикует состояние в новый жизненный цикл

### Requirement: Architectural boundaries

Приложение MUST разделять чистую domain-логику, команды application, native adapters и UI, сохраняя Expo и локальную SQLite. Контракт UI MUST быть независимым от внутренней реализации hook.

#### Scenario: Тестирование команд без UI

- **WHEN** тест выполняет команду расписания/остатка с fake repository, clock и IDs
- **THEN** не требуется импорт React Native, Expo Notifications или запуск телефона

#### Scenario: Владение экраном и формой

- **WHEN** открывается один из четырёх маршрутов
- **THEN** он использует выделенный экран, общий shell и только необходимые диалоги; вычисления закрытой истории не выполняются

### Requirement: Accessible platform UI

Интерфейс MUST сохранять читаемость, доступные имена/состояния и достижимость действий на поддерживаемых телефонах/планшетах с клавиатурой, системными inset и крупным шрифтом.

#### Scenario: Работа со screen reader

- **WHEN** пользователь проходит формы и действия с VoiceOver или TalkBack
- **THEN** поля имеют осмысленные имена, ошибки/pending объявляются, история открывается понятной кнопкой и удаление доступно без свайпа

#### Scenario: Маленький экран и split view

- **WHEN** открыта модальная форма с клавиатурой на маленьком экране либо в узком планшетном окне
- **THEN** поля, ошибки, закрытие и сохранение доступны прокруткой; кнопки не рассчитываются шире контейнера и не перекрываются системными элементами

#### Scenario: Варианты native кнопок

- **WHEN** используются primary, secondary, danger и disabled
- **THEN** семантика и доступность соответствуют варианту на обеих платформах, включая fallback старой iOS

### Requirement: Bounded history work

Работа с историей MUST ограничивать ненужные вычисления и число одновременно отображаемых записей; выбор оптимизаций MUST опираться на измерения release-сборки.

#### Scenario: Закрытая большая история

- **WHEN** в базе 10 000 intake-записей, история закрыта и изменён один приём
- **THEN** закрытый диалог не сортирует и не монтирует всю историю
- **AND** замер команды и UI-отклика на выбранных устройствах приложен к приёмке

#### Scenario: Открытие большой истории

- **WHEN** пользователь открывает историю на том же наборе данных
- **THEN** отображение ограничено страницей/окном, доступ ко всем записям сохранён и нет длительной блокировки интерфейса

### Requirement: Local data privacy and erasure

Приложение MUST точно описывать локальное хранение, OS backup/transfer и очистку. Пользовательские данные MUST NOT отправляться на сервер Pillo. Очистка MUST удалять относящиеся к приложению данные и напоминания согласно объявленной политике.

#### Scenario: Проверка backup policy

- **WHEN** собираются release-приложения
- **THEN** проверены применённые backup/transfer rules для SQLite и recovery-копий
- **AND** формулировка «только на устройстве» используется только при подтверждённом исключении облачного backup; отдельное шифрование не заявлено без реализации

#### Scenario: Очистка и перезапуск

- **WHEN** пользователь подтверждает «Удалить все данные» и снова запускает приложение
- **THEN** прежние препараты, история и собственные recovery-копии не возвращаются, связанные уведомления удалены либо явно показан незавершённый системный шаг с повтором
- **AND** интерфейс не обещает физическое стирание носителя, если выполнена только логическая очистка

### Requirement: Accurate product documentation

Документация MUST описывать текущий автономный native-продукт, реальные ограничения и проверки. Историческое веб-описание MUST быть отделено от действующих требований.

#### Scenario: Чтение README новым разработчиком

- **WHEN** разработчик следует README
- **THEN** он получает актуальные команды двух платформ, минимальные ОС, политику данных и точное описание уведомлений/очистки без несуществующих server/auth/email-функций

### Requirement: Verified cross-platform release

Готовность MUST подтверждаться регрессионными тестами, совместимостью зависимостей, triage security advisory и native-проверками обеих платформ. Успешный JS export MUST NOT считаться native/device acceptance.

#### Scenario: Завершение технических проверок

- **WHEN** этап реализации объявляется проверенным
- **THEN** записаны команды/exit codes TypeScript, тестов, lint, exports и актуальной Expo compatibility-проверки
- **AND** оставшиеся npm advisory имеют оценку достижимости и решение; force downgrade не используется как автоматическое исправление

#### Scenario: Готовность к выпуску

- **WHEN** приложение предлагается к выпуску
- **THEN** есть доказательства native release-сборки, установки/обновления с v1 и матрицы устройств для iOS/Android, включая уведомления, миграцию и accessibility
- **AND** непроведённые проверки обозначены открытыми, а публикация остаётся отдельным действием
