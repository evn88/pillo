# Целевая архитектура и решения

## 1. Границы решения

Expo / React Native остаются основной платформой. Приложение работает без аккаунта и прикладного сервера. Источник истины — успешно сохранённые локальные данные. Уведомления — производное системное состояние, которое может отставать и нуждаться в восстановлении.

Ниже предложены конкретные решения для реализации. Это новая спека, не описание уже работающего поведения. Изменения формата БД, dependencies и native permissions выполняются только на соответствующем этапе реализации с проверкой миграции и обеих платформ.

## 2. Распределение ответственности

```text
app/                         маршруты Expo Router, root providers
src/screens/                 today, medications, schedule, settings
src/components/              общие представления, формы, native UI adapters
src/domain/                  типы, валидация, календарь, stock transitions, selectors
src/application/             команды, bootstrap, day lifecycle, notification reconciliation
src/storage/                 контракт repository, SQLite, codec, миграции
src/services/                контракт уведомлений, Expo native adapter
src/hooks/                   React-подписки и локальное состояние форм
src/providers/               композиция зависимостей и React context
src/theme/                   токены и один контракт темы
```

Это направления разделения, не требование создавать файл для каждой функции. Сначала извлекать код по реальным зависимостям. Избегать общего framework/repository factory, event bus и сервисного контейнера.

| Слой | Разрешено | Не должно находиться здесь |
| --- | --- | --- |
| Domain | Чистые функции и типы, переданные now/ID, проверка инвариантов | React, Expo, SQLite, Alert, таймеры |
| Application | Последовательность команд, результат, вызовы контрактов, lifecycle | JSX, стили, прямые OS-вызовы |
| Adapters | SQLite, Notifications, системные разрешения | Решение, какая доза допустима и как меняется история |
| UI | Отображение view model, локальный ввод, вызовы действий | Запись БД, scheduling, арифметика учёта |

Clock и ID generator передаются в тестируемые команды. Достаточно небольших функциональных контрактов. `PilloState`, `PilloActions`, `CommandResult`, `Repository`, `NotificationGateway` определяются явно, не через ReturnType React-hook.

На первом этапе достаточно Context со стабильными actions и отдельным state-представлением. Не заменять локальные данные на TanStack Query и не копировать snapshot в Zustand. Выделять подписки/селекторы по измеренной необходимости.

Каждый route создаёт собственный screen. Общий shell не создаёт все модальные формы на каждой вкладке. История монтируется или вычисляется по запросу. Один theme hook возвращает palette/isDark; цвет не используется как идентификатор темы.

## 3. Сохранение и команды

Выбран начальный **пессимистичный commit**: UI показывает pending, подтверждённый snapshot публикуется после успешной записи. Для локального приложения это проще и безопаснее нескольких optimistic rollback. Если измерения покажут заметную задержку, оптимизм вводится отдельно с revision-aware протоколом.

Последовательность команды:

1. Принять и проверить ввод; создать стабильный command ID на пользовательское намерение, а не на каждый render.
2. Поместить команду в очередь единственного writer; считать её относительно последнего подтверждённого состояния внутри очереди.
3. Чистой функцией вычислить новое состояние, stock effects и необходимость notification reconciliation.
4. Сохранить новую ревизию и reconciliation metadata атомарно.
5. Опубликовать подтверждённое состояние и результат команды.
6. Отдельно запустить/coalesce notification reconciliation; его ошибка не отменяет записанный факт.

`CommandResult` различает success, validation error, persistence error, unavailable. Сохранённые данные с проблемой уведомлений — success плюс отдельный warning/status, а не предложение повторить создание сущности.

Queue не блокирует дальнейшие команды навсегда после reject. Один повтор намерения не создаёт ещё одну запись; два отдельных подтверждённых пополнения добавляют две упаковки. На UI pending привязан к конкретной операции/форме, а глобальный статус отображает фактический объём очереди.

Запись выполняется вне React updater и render. Простая замена на `setState(prev => ...)` с `save()` внутри updater недопустима. Gesture callbacks получают актуальный handler; сохранённое замыкание не является хранилищем состояния.

## 4. Валидация и единицы

Общие валидаторы используются формами, командами и decoder БД. Формы показывают field errors и сохраняют ввод после отказа. Согласно инструкциям проекта — RHF со schema validation; выбор поддерживаемой схемы и RN testing adapter оформляется в этапе tooling, без установки web-only компонентов.

- Разрешить запятую и точку как десятичный разделитель, trim по краям; не принимать смешанные разделители и частично распарсенные строки.
- Доза строго положительная и конечная; остаток и порог неотрицательны. Упаковка положительна, если действие пополнения доступно; для legacy=0 действие отключено до исправления.
- Не подставлять дозу 1 вместо неправильного ввода, не округлять вверх до 0.25.
- Проектное решение по точности: до 3 десятичных знаков, операции в целых тысячных единицы в безопасном диапазоне integer. Это ограничение формата учёта, не рекомендация по дозированию. Избыточную точность отклонять с объяснением, а не округлять молча.
- Формат даты строго YYYY-MM-DD с календарной проверкой; HH:mm в пределах 00:00–23:59; daysOfWeek — непустое множество 0…6; endDate ≥ startDate.
- Проверять наличие/доступность лекарства, уникальность ID и связи. isActive имеет одинаковую семантику в планировании и UI; неактивные лекарства не получают новые события.
- Размеры строк/коллекций и допустимые numeric bounds задаются явно, без появления бесконечных JSON-значений.

Нативные date/time pickers можно использовать через уже выбранный Expo UI после проверки SDK 57; валидатор всё равно остаётся на границе команды. Quick intake открывает выбор дозы либо явно показывает и подтверждает количество; нажатие карточки не регистрирует факт незаметно.

## 5. Учёт остатка и история

Доза фактического приёма и величина списания учётного остатка — разные данные. Нельзя запрещать пользователю зарегистрировать уже случившийся приём только потому, что запас в приложении неточен.

Предлагаемый контракт:

- При TAKEN применить `min(stock, dose)` и сохранить величину применённого списания в событии; при дефиците показать расхождение учёта.
- Undo возвращает именно применённое списание. Идемпотентный повтор того же статуса не меняет запас или время факта.
- Пополнение и ручная корректировка запаса оформляются явными командами. Undo одного приёма не откатывает другие пополнения/приёмы.
- Для MANUAL отмена удаляет/аннулирует ручной факт с возвратом его stock effect; не создаёт фиктивный плановый PENDING. Для SCHEDULED отмена возвращает PENDING только согласно календарной политике.
- Исторический факт хранит контекст лекарства и дозы на момент отметки, source, плановую дату/время и фактическое время перехода. Переименование лекарства не меняет подписанный прошлый факт.
- Удаление правила сохраняет TAKEN/SKIPPED и прошлые неотмеченные события. Отдельное подтверждённое уничтожение препарата с его историей и «Удалить всё» сохраняются как явные разрушительные сценарии.

Legacy: исходная БД не содержит реально списанную величину. Нельзя достоверно восстановить её из текущего остатка. Миграция маркирует такие эффекты unknown; при отмене старой записи приложение требует явного решения по корректировке остатка и не применяет выдуманный возврат. Старые названия на момент факта также невосстановимы: перенесённый контекст помечается как восстановленный из текущего справочника.

## 6. Календарь и изменения правил

По умолчанию правило означает **местное время устройства**. При путешествии будущие события следуют новому местному времени; уже зарегистрированные факты сохраняют исходный localDate/time, timestamp и, для новых записей, timezone-контекст. Поддержка фиксированной «домашней timezone» — отдельная функция.

Единый lifecycle coordinator сверяет календарь при старте, foreground, смене календарного дня и обнаруженной смене timezone. В активном приложении допускается таймер до следующей местной полуночи; в фоне на него полагаться нельзя.

Правки применяются к ещё не наступившим PENDING. Их время/доза/лекарство пересобираются, более не действующие экземпляры удаляются. TAKEN/SKIPPED и уже наступившие неотмеченные события сохраняются. Повторная правка не создаёт второй приём для уже завершённого occurrence. Более сложный сценарий второго приёма оформляется отдельным правилом или ручной записью.

Для перехода DST:

- Несуществующее местное время не пропускается молча: предложенное поведение — перенести к первому существующему времени после разрыва с сохранением исходного планового времени и отображением переноса.
- Повторяющееся время осенью даёт один occurrence, выбран первый instant. UI и Notifications используют одно и то же разрешение даты.
- Эти решения покрываются тестами timezone/DST и проверкой реальных триггеров. Повторяющийся OS trigger допускается только если его поведение соответствует этому контракту; иначе использовать явные даты/адаптер.

Дни, когда приложение не открывалось, нельзя автоматически считать сознательно пропущенными. Новая версия хранит материализованные экземпляры на 35 дней вперёд и интервалы доказанного покрытия; если доказанного покрытия нет (в частности, у legacy), показывает неизвестный период. Прошлые PENDING видны как «не отмечено», отдельно от SKIPPED. В архитектурном этапе выбран ограниченный расчёт сегодня + 35 дней. Сохранённые экземпляры представляют прошлый известный план; интервалы за пределами покрытия не восстанавливаются сегодняшним правилом. Отдельный журнал ревизий правил не нужен для этого ограниченного контракта; не добавлять backfill неизвестных периодов без новой спецификации.

## 7. Уведомления как восстановимая проекция

Небольшой reconciliation coordinator достаточен: отдельная таблица/версионированная запись метаданных, один worker и gateway. Не нужен сервер или полноценный message broker.

Вместе с изменением данных атомарно сохраняются desiredRevision и признак pending reconciliation. Coordinator читает подтверждённую ревизию, строит желаемый набор и сравнивает с зарегистрированными системными событиями. Стабильный ID включает occurrence/date и поддерживает изменение версии. Активная сверка не может объявить более новую ревизию выполненной. При новой команде выполняется ещё один проход по последней версии.

OS API не транзакционен с SQLite. Поэтому хранить appliedRevision, lastError и дату подтверждённого покрытия; при сбое восстанавливаться идемпотентно. Сначала вычислить/валидировать план и проверить доступность, затем менять конкретные события. Не удалять всю рабочую очередь перед каждой попыткой.

Не пересоздавать напоминания при смене темы или ином нерелевантном поле. Ранняя TAKEN/SKIPPED удаляет соответствующее будущее напоминание; undo восстанавливает его, если время ещё актуально. Для recurring trigger отдельно подтвердить возможность исключить одно событие, сохранив остальные; простое repeat без этой возможности не проходит приёмку.

### Покрытие без открытия приложения

Доступные стратегии проверить в небольшом native spike до окончательной реализации:

1. Системные повторения для поддерживаемых регулярных правил, с доказанной обработкой начала/конца курса, одноразовых исключений и DST.
2. DATE-триггеры для нерегулярных/ограниченных правил; capacity-aware очередь и честное `coverageEndsAt`.
3. Если Expo API не покрывает принятый контракт — небольшой Swift/Kotlin-адаптер. Это не повод переписывать UI.

Целевой проверочный сценарий: 10 ежедневных напоминаний, 35 дней без открытия и без сети. Для поддержанного режима ожидается полное покрытие. Если достижение невозможно при выбранных API/ограничениях ОС, режим должен быть явно ограничен до включения и в настройках показана дата окончания покрытия. Нельзя считать 60 созданных событий выполнением 30-дневного покрытия. Не обещать гарантированное выполнение фонового JS или обход force-stop/Focus.

Настройки разделяют requestedEnabled, authorization, channel/system availability, exact capability, sync state. Denied не превращается в вечный автоматический запрос при запуске; предлагается открыть системные настройки. iOS provisional обозначается как тихая доставка, не полный отказ. Android exact-alarm access проверяется отдельно от POST_NOTIFICATIONS; permission/config выбирать по фактическому требованию точности и актуальной документации ОС.

Notification response ждёт загрузки БД, валидирует payload и открывает нужный контекст. Устаревшие/удалённые события показывают нейтральный fallback. Нажатие само не меняет дозу, статус или запас. Название и доза остаются скрыты в системном тексте.

## 8. Хранилище, миграции и восстановление

Сохранить SQLite. На первом этапе допустимо оставить snapshot payload, добавив version/revision/metadata и строгий codec. Одна UPDATE целого JSON уже атомарна сама по себе; транзакция нужна для связанных записей и миграций. Нормализовать все таблицы заранее не требуется.

- Отличать new DB, supported version, unsupported newer version и corrupt DB/payload.
- Не понижать user_version. Версию менять только после успешной транзакции миграции.
- Decode в unknown, проверить schema и domain invariants до использования/перезаписи.
- Отсутствующую строку при существующей версии считать ошибкой целостности; создание empty state допустимо только для достоверно новой базы.
- Проверять количество записанных строк. Сбой записи не публикует новый snapshot.
- На старте не требовать записи неизменившегося snapshot ради отображения уже прочитанных данных.
- Один владелец handle; close на ошибке открытия/конфигурации и корректное завершение после отмены bootstrap.
- Before migration сохранять безопасную локальную резервную копию согласованной БД/payload; raw copy одного db-файла при активном WAL не считается корректным backup. Проверить доступный SQLite backup API SDK 57.
- При неизвестной версии/повреждении сохранить исходные данные, предложить retry/recovery. Автоматический reset запрещён.

Миграция добавляет только сведения, которые можно обоснованно получить. Stock effects и исторические названия с неизвестным прошлым помечаются явно. После миграции проверить count/ID/статусы/остатки/settings и повторное открытие. Откат к старому бинарнику после смены схемы отдельно определяется; «старое приложение перезапишет новую схему» недопустимо.

## 9. Приватность и очистка

Предлагаем сохранить точную формулировку: «Приложение хранит данные локально и не синхронизирует их с сервером Pillo». Для обещания «только это устройство» требуется дополнительная проверка резервного копирования ОС.

Исходя из текущего обещания local-only, рекомендуемое решение — исключить БД из облачных OS backup и отдельно проверить device-to-device transfer на обеих ОС. Фактические manifest/entitlements/backup rules должны проверяться в собранном приложении. Ограничение означает риск потери данных при утере устройства; пользовательский экспорт/восстановление — отдельное будущее изменение, не скрытая cloud-функция.

«Удалить все данные» очищает прикладные записи, локальные recovery-копии этого приложения и системные напоминания, переживает повторный запуск; операция имеет явный результат и повтор сверки при сбое OS API. Документация должна точно говорить, выполняется логическая очистка или удаление файлов. Не обещать невозможность восстановления на уровне носителя. Не удалять другие файлы устройства.

Дополнительное шифрование/биометрия потребуют отдельной модели угроз, управления ключом и recovery. Одного переименования vault в secure store для гарантии защиты недостаточно.

## 10. UI, производительность и инструменты

Сохранить текущую структуру четырёх разделов и платформенный характер управления. Исправления accessibility/safe areas не являются поводом для полного редизайна.

- Именованные поля, сообщения об ошибках, доступные pending/status, понятные действия для VoiceOver/TalkBack.
- Размеры от контейнера, учёт native tabs и inset, модальные формы с клавиатурой, Dynamic Type и split view.
- Единый контракт primary/secondary/danger и disabled для SwiftUI/Universal кнопок.
- Доступная альтернатива свайпу; не конфликтующие вложенные нажатия; актуальные callback.
- Закрытая история не сортирует полный массив. История на 10 000 записей профилируется в release; при необходимости SectionList/FlatList или уже обоснованная библиотека. Новая библиотека списков не обязательна.
- Измерить update latency на выбранном бюджетном Android и iPhone, память и число rendered rows; предложенный бюджет локальной команды p95 ≤200 ms на синтетических 10 000 записях, без длительных UI-подвисаний. Если не достигнут — сначала определить причину, затем нормализовать/пагинировать.
- Добавить lint/rules-of-hooks и минимальные ограничения import layers; не форматировать весь проект.
- Проверить `sf-symbols-typescript` как прямую зависимость либо использовать публичный тип Expo UI.
- Совместимое обновление SDK 57 и security triage до новых зависимостей; не запускать `audit fix --force`.

## 11. Проверки и риски

Unit: domain validators/calendar/stock. Application: fake clock/IDs/repository/notification gateway, concurrency, failures и retries. Adapter: настоящая SQLite-транзакция/миграция на поддерживаемом окружении; mocks не доказывают работу native SQLite. UI: React Native Testing Library с user-event и корректным RN runner/transform; совместимость с текущим Vitest проверить до выбора конфигурации. Device: реальные iOS/Android release builds.

Матрица должна включать минимальные поддерживаемые ОС SDK 57 (по текущей документации iOS 16.4+, Android 7+) и актуальные ОС; отдельно Android 12/13/14+ для alarms/permissions, iOS с новым и fallback UI, планшет/split view, большой шрифт и закрытое приложение. Минимальные ОС перепроверяются при выборе финальных версий.

Риски реализации: изменение формата требует неразрушающей миграции; native scheduling не даёт абсолютной гарантии доставки; legacy stock effect невосстановим; общая snapshot-запись может потребовать нормализации после замера; security findings могут относиться к tooling и иметь несовместимые автоматические исправления. Все эти случаи отражаются в приёмке, а не скрываются флагом «готово».

## 12. Зафиксированное решение архитектурного этапа

Реализовано ядро в текущем дереве, см. handoff.md и отметки tasks.md.

- Формат `PilloDocument.schemaVersion=2`, CAS по SQL `revision`, один последовательный writer. Контекст React теперь имеет явный контракт и стабильные actions.
- Snapshot пока остаётся одним JSON. Числа вычисляются в тысячных единицы, диапазон 0…1 000 000 000; избыточная точность не округляется молча. Несовместимые legacy-данные дают восстановимый отказ с сохранением оригинала.
- Recovery исходного payload v1 находится в таблице `pillo_recovery` внутри той же транзакции миграции. Это защита от ошибки преобразования, не независимая резервная копия от повреждения всего файла. При явной очистке данные и recovery удаляются атомарно.
- История сохраняет название/дозировку, recordedAt и реальный stockEffectUnits; legacy effect неизвестен. API отмены принимает явно подтверждённый legacyStockReturnUnits, но окончательный UI такого подтверждения остаётся следующему этапу. Отдельное поле исторической timezone ещё не добавлено; не считать этот пункт design.md выполненным.
- Controller строит план из сохранённых occurrences, desired/applied revision записываются в БД. Одноразовые DATE-триггеры имеют стабильные ID и fingerprint, сверяются без глобального cancel-all. Зафиксирована ёмкость 60 событий; дата покрытия ограничивается первым невместившимся событием и доказанным календарным интервалом.
- Эта ёмкость консервативна, не объявляется измеренным лимитом каждой ОС. Системные повторения, exact alarms и автономные 35 дней требуют spike/устройств; ограниченный режим уже отображает дату покрытия. UX предупреждения до включения ещё требует завершения.
- Adapter SDK и зависимости не обновлялись; RHF/schema-library/lint не устанавливались. Текущие формы временно адаптированы к CommandResult, общему decimal parser и повторяемому command ID; это переходный UI-контракт, не завершение UI-этапа.
- Автоматический запуск старого бинарника v1 поверх БД v2 не поддерживается: старый код не проверяет newer version. Для отката нужен контролируемый возврат согласованного v1 payload/БД, а не изменение PRAGMA вручную. Пользовательский recovery-интерфейс и проверка upgrade/restore на телефонах остаются открытыми.
