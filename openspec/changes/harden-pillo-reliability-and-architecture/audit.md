### Уровни доказательств

- **Код** — конкретная ветка и её следствие прослеживаются в исходниках; это не утверждение о тестировании на телефоне.
- **Воспроизведено** — дополнительно выполнен прямой вызов текущей чистой функции либо точного выражения из кода.
- **Риск/пробел** — необходима проверка на устройстве, проверка достижимости зависимости или продуктовое решение; неисправность не объявляется доказанной.
- P1 — устранить до выпуска: корректность данных, напоминаний и критические непроверенные зависимости. P2 — следующий обязательный слой качества/архитектуры, допускающий обоснованный отдельный этап. P0 в этом аудите не присваивался.

## Реестр

### A01 · P1 · Ошибка открытия оставляет бесконечную загрузку — код

`src/hooks/use-pillo.ts:37`: catch записывает `error`, но не меняет `status='checking'`. `App.tsx:67` показывает только spinner; `error` вообще не читается UI. Повреждённый JSON, ошибка открытия или начального сохранения дают экран без объяснения и повторной попытки. `unlock` не экспортируется.

Исправление: отдельное состояние ошибки и повторная попытка, сохранение исходных данных, разделение чтения и необязательного обслуживания. Приёмка: ошибка load/save при запуске показывает доступный экран восстановления, retry после устранения причины открывает исходные данные.

### A02 · P1 · Неуспешное сохранение выглядит успешным — код

`use-pillo.ts:64–79`: `commit` проглатывает ошибку; вызывающий код получает fulfilled Promise. Формы закрываются, глобальные `error`/`isSaving` не отображаются. `ScheduleForm` вообще не блокирует повторное сохранение. Ошибка уведомлений после успешного сохранения может оставить форму открытой без объяснения, а повторное создание — добавить ещё одно правило.

Исправление: явный результат команды с разделением отказа сохранения и предупреждения о напоминаниях; pending и field/global errors. Приёмка: отказ SQLite не закрывает форму и не теряет ввод; повторная попытка не создаёт дубликат.

### A03 · P1 · Конкурентные команды используют устаревший snapshot — код

`use-pillo.ts:68`: `previous = snapshot` берётся из замыкания, нет очереди. Два вызова до следующего render либо rollback первой записи после второй могут потерять изменения. Один boolean `isSaving` также не отражает несколько операций. Вычисление `nextRules` до `commit` усиливает проблему.

Исправление: один сериализованный исполнитель, актуальное подтверждённое состояние внутри команды, стабильные идентификаторы повторов. Приёмка: две разные команды сохраняются обе; ошибка первой не откатывает последующую успешную; UI и повторное чтение БД совпадают.

### A04 · P1 · Полный свайп вызывает старый обработчик удаления — код

`src/components/swipeable-card.tsx:44`: сохранённый через `useRef` PanResponder удерживает первоначальный `deleteCard/onDelete`. После последующих правок карточки полный свайп вызывает старую цепочку, включая старый `deleteMedication`/`deleteScheduleRule` и snapshot из A03. Нажатие открытой кнопки удаления использует другой, свежий обработчик.

Исправление: актуальный callback при стабильном responder и команды, независимые от замыканий UI. Приёмка: создать A, затем B, изменить B, удалить A полным свайпом — B и его изменения сохраняются. Отдельно проверить отмену подтверждения и обычное нажатие.

### A05 · P1 · Числовой ввод молча меняет дозу и остаток — воспроизведено

`manual-intake-sheet.tsx:26`, `schedule-form.tsx:48`, `medication-form.tsx:55`: `Number(value) || fallback` и clamp подменяют пользовательский ввод. В интерфейсе прямо предложен формат `0,5`, но сохраняется `1`; `0` также становится `1`, отрицательная доза — `0.25`. `Infinity` проходит выражение и при JSON-сохранении становится `null`. Остаток `0,5` превращается в `0`.

Исправление: общий строгий парсер десятичных чисел с запятой/точкой, finite/range/precision validation, никакого исправления дозы без пользователя. Приёмка: `0,5` = `0.5`; пустое, отрицательное, `Infinity`, `NaN`, мусор блокируют сохранение с объяснением.

### A06 · P1 · Нет полноценной валидации расписаний и команд — воспроизведено/код

`schedule-form.tsx:140`: regex принимает `99:99`; даты не валидируются, endDate может предшествовать startDate. `materializeIntakesForDate` создаёт приём `99:99`, а `getUpcomingRuleDates` для него не создаёт уведомлений. `fromLocalDateTime` принимает лишние сегменты вроде `2026-09-13-extra`. Прямые команды не проверяют существование лекарства, положительную конечную дозу, уникальные/допустимые дни и активность лекарства.

Исправление: общая валидация на границе команд и данных; UI использует те же правила. Приёмка: календарно невозможные даты, неверное время и отсутствующие связи отвергаются до записи и побочных эффектов.

### A07 · P1 · Отмена приёма создаёт запас — воспроизведено

`use-pillo.ts:171–191`: списание ограничивается нулём, возврат всегда равен полной дозе. Остаток `0.5`, доза `1`: после приёма `0`, после отмены `1`. Аналогично запись ручного приёма и её отмена через «Сегодня». Модель не хранит реально применённое изменение остатка; float-арифметика не имеет политики точности.

Исправление: сохранять фактически применённое изменение, отделять зарегистрированный факт приёма от учётного остатка. Приёмка: take → undo восстанавливает `0.5`, повтор того же статуса не меняет запас, пополнение между операциями не теряется.

### A08 · P1 · Смена дня не материализует новый план — код

`use-pillo.ts:27–45,139`: материализация только при запуске и сохранении правила. Нет реакции на foreground, полночь, timezone. `new Date()` в render сам не инициирует render. После ночи приложение может показывать вчерашнее состояние либо пустой новый день при очередном render, хотя действующие правила есть.

Исправление: lifecycle coordinator с единой датой/часами, повторная идемпотентная сверка на foreground и полночь. Приёмка: оставить приложение через полночь и вернуть из фона после нескольких дней — текущий план появляется без перезапуска и дубликатов.

### A09 · P1 · Правка правила не пересобирает существующие приёмы — воспроизведено

`src/domain/schedule.ts:53–69`, `use-pillo.ts:139–158`: существующий `ruleId:date` только исключается из вставки. Изменение времени `09:00 → 10:00`, дозы `1 → 2` или препарата оставляет старую карточку; уведомления строятся уже по новому правилу. Выключение дня/правила также не удаляет старый PENDING. Завершённые факты, напротив, действительно следует сохранять.

Исправление: явное согласование ожидающих будущих приёмов и сохранённой истории. Приёмка: карточка и уведомление для изменяемого будущего приёма совпадают; завершённый приём и его остаток не переписываются.

### A10 · P1 · Удаление правила уничтожает прошлую историю вопреки подтверждению — код

`App.tsx:159` обещает удалить будущие приёмы. `use-pillo.ts:161–168` удаляет все записи с `scheduleRuleId`, включая TAKEN и SKIPPED; ранее списанный запас остаётся списанным. Удаление препарата тоже каскадное, но там UI предупреждает об истории — это отдельный явно подтверждённый сценарий, не тот же обман ожиданий.

Исправление: архивирование правила либо сохранение фактов независимо от него, удаление только допустимых будущих PENDING. Приёмка: удаление правила сохраняет предыдущие факты и запас; уничтожение истории препарата остаётся отдельным явным подтверждением.

### A11 · P2 · История неполна и меняется вслед за справочником — код/пробел модели

`history-sheet.tsx:29` скрывает все PENDING. Дни без запуска не материализуются, поэтому отсутствие записей выглядит как отсутствие плана. Название берётся из текущего Medication: переименование переписывает видимое прошлое. Для SKIPPED нет времени отметки, фактическое `takenAt` не показано. Кнопка «Принять сейчас» в `App.tsx:376` сразу регистрирует ровно 1 ед., не показывает это количество заранее.

Исправление: отличать «не отмечено» от сознательного пропуска и неизвестного периода; хранить контекст факта, показывать плановое/фактическое время; явный выбор дозы для быстрого ручного приёма. Не вычислять adherence по неполным данным.

### A12 · P1 · Напоминания заканчиваются после первых 60 событий — код

`notifications.native.ts:52–59`: окно дат 30 дней обрезано до 60 отдельных DATE-триггеров. При 6 событиях в сутки это около 10 дней. Возобновление только через вызовы приложения; автономного пополнения окна нет. README формулирует окно как 30 дней без оговорки о фактической ёмкости.

Исправление: определить поддерживаемое покрытие и комбинировать допустимые повторяющиеся/одноразовые системные триггеры, явную дату покрытия и сверку. Не обещать бесконечный фоновый JavaScript. Приёмка: плотное расписание и длительное отсутствие проверены на обеих ОС; исчерпание ёмкости не маскируется состоянием «всё работает».

### A13 · P1 · Перепланирование не связано с успешным commit и конфликтует само с собой — код

`notifications.native.ts:44` сначала отменяет всё, затем проверяет разрешение и последовательно создаёт очередь. Падение в середине оставляет частичный план. Несколько одновременных запусков могут отменять/дублировать события друг друга. После ошибки `commit` вызывающий метод всё равно планирует несохранённые данные. Смена темы через `updateSettings` также полностью пересоздаёт напоминания.

Исправление: отдельная последовательная сверка только подтверждённого snapshot, идентификаторы событий, сохранённый признак необходимости повтора, сравнение желаемого и системного плана. Приёмка: ошибка третьего scheduling-вызова, перезапуск и быстрые правки сходятся к последней сохранённой версии без дублей и «призрачных» событий.

### A14 · P1 · Переключатель не отражает фактические разрешения и точность — код/платформенный риск

`requestNotificationPermission` проверяет только `granted`; `updateSettings` сохраняет true до запроса разрешения. Ошибка не показана. В `app.json` нет настройки exact alarms; установленный `expo-notifications` при отсутствии `canScheduleExactAlarms()` использует `setAndAllowWhileIdle` вместо точного варианта. Это подтверждает fallback, но не измеряет задержку конкретного телефона. На iOS нужны отдельные состояния provisional/denied/authorized, а не один boolean.

Исправление: разделить желание пользователя, разрешение ОС, возможности точного времени и фактический статус планирования. Приёмка: отказ/отзыв разрешения, Android exact access, выключенный канал и iOS provisional представлены честно; возврат из Settings запускает сверку. Boot receiver уже добавляет библиотека — его отсутствие в `app.json` не ошибка.

### A15 · P1 · Уведомления не учитывают завершённые приёмы — код

`rescheduleNotifications` получает только лекарства/правила/settings; статусы приёмов неизвестны. `setIntakeStatus` не отменяет уведомление. Отметка утреннего приёма заранее не убирает его будущее напоминание; очередная сверка снова запланирует его.

Исправление: план строится с учётом экземпляров приёмов и статусов. Приёмка: ранняя TAKEN/SKIPPED отменяет только соответствующее событие, undo восстанавливает ещё актуальное напоминание; будущие дни остаются.

### A16 · P2 · Нажатие уведомления не связано с конкретным приёмом — код/улучшение

Payload содержит `ruleId`/`medicationId`, но нет даты/идентификатора occurrence. В проекте нет обработчика notification response или стартового response. Открытие приложения системой само по себе возможно, но переход к нужному приёму не реализован.

Исправление: идентификатор события, обработка cold/warm start после загрузки БД, валидация payload, безопасное поведение для удалённого/устаревшего события. Само нажатие уведомления не должно списывать препарат.

### A17 · P1 · Данные из JSON считаются типобезопасными без проверки — код

`vault.native.ts:47`: `JSON.parse(...) as PilloSnapshot`; нет проверки shape, чисел, enum, дат, связей и дубликатов. Синтаксически корректный повреждённый payload может сломать рендер или сохраниться поверх исходного при начальной материализации. Настройка TypeScript strict не защищает границу JSON.

Исправление: декодировать unknown, проверить версию и инварианты, оставить исходный payload неприкосновенным при отказе. Приёмка: некорректный JSON/shape/связь даёт восстановимый отказ без записи пустого snapshot.

### A18 · P1 · Схема может понизить версию и молча не сохранить строку — код

`vault.native.ts:31` всегда устанавливает `user_version=1`, даже если обнаружена более новая база. При версии ≥1 и отсутствующей строке `id=1` load возвращает emptySnapshot, а UPDATE меняет 0 строк и считается успешным. Создание/миграция не оформлены одной транзакцией; версия payload не определена.

Исправление: монотонные транзакционные миграции, политика новой/повреждённой/будущей базы, проверка числа записанных строк. Приёмка: newer-version база не изменяется; missing row не даёт ложного успеха; прерванная миграция сохраняет исходное состояние.

### A19 · P2 · Не определён владелец SQLite-соединения — код

`VaultHandle.close` нигде не вызывается; начальный effect не имеет cleanup/cancellation, отказ конфигурации/загрузки не закрывает открытый handle. Повторное монтирование провайдера может открыть ещё одно соединение и оставить асинхронный запуск без владельца. Это дефект жизненного цикла, не доказательство утечки при каждом обычном запуске.

Исправление: один владелец подключения, идемпотентное открытие, cleanup без закрытия используемого соединения. Приёмка: mount/unmount/remount и ошибка инициализации не оставляют активных забытых handles или writes после dispose.

### A20 · P2 · Слои связаны через большой hook и универсальный экран — код

`App.tsx` содержит 556 строк, четыре экрана, общий chrome, формы, подтверждения, селекторы и стили. Все четыре маршрута создают экземпляр `PilloApplication` со всеми modal-компонентами. `usePillo` совмещает предметные команды, UUID/clock, React, persistence и Notifications. Контекст экспортирует `ReturnType<typeof usePillo>` вместо независимого контракта. Тема определяется повторно, а в `ActionButton` выводится из сравнения цвета.

Исправление: разделение по ответственности из design.md без замены всего стека. Приёмка: предметные команды тестируются без React Native, UI не импортирует SQLite/Notifications, каждый маршрут владеет только своими экранами/диалогами, явные типы состояния и действий.

### A21 · P2 · Доступность и геометрия имеют неподтверждённые ограничения — код/риск

У большинства TextInput нет явной accessibility-связи с подписью; соседний Text сам не гарантирует label. Android History рисует glyph-кнопку внутри View с ролью button — нужно проверить фактическое дерево TalkBack. Full-screen Modal не учитывают safe-area явно; ScheduleForm не имеет keyboard avoidance. Ширина native-кнопок вычисляется от окна, а формы ограничены 680 pt; фиксированы высоты 56/60 и footer bottom=88. `tone='secondary'` фактически не отличается от primary; Android UniversalButton всегда outlined. Вложенные действия внутри свайпа требуют проверки.

Исправление: доступные имена, единая семантика вариантов, размеры от контейнера и системных inset, keyboard-aware формы. Приёмка: VoiceOver/TalkBack, крупный шрифт, маленький экран, split view/rotation, клавиатура и Android back; не заявлять конкретное перекрытие без запуска.

### A22 · P2 · Рост истории увеличивает стоимость каждого действия — код/риск производительности

Каждая запись сохраняет полный JSON со всей историей. HistorySheet копирует, сортирует и группирует все записи даже при `visible=false`; `.map` внутри ScrollView не ограничивает число элементов. Общий context уведомляет всех потребителей. Группировка дополнительно копирует массив записей группы. `icon-pillo.png` размером 1 059 930 байт используется для маленького логотипа и попадает в оба bundle.

Исправление: не вычислять закрытую историю, страничное/виртуализированное отображение по замерам, стабильные селекторы, компактный отдельный ресурс логотипа при необходимости. Переход к нормализованным таблицам делать по результатам профиля, а не автоматически. Приёмка: замер на устройстве с 10 000 intake-записей; ограниченный render и отсутствие потери UI-отклика при сохранении.

### A23 · P2 · Не определена политика резервных копий и очистки — код/риск приватности

Приложение использует обычную SQLite, без SQLCipher/отдельной блокировки, но UI говорит «Все данные защищены». Это не означает отсутствие системной защиты sandbox. Expo Android AllowBackup plugin по умолчанию возвращает true; `app.json` это не переопределяет. Поэтому утверждение «данные остаются на этом устройстве» требует проверки OS backup/переноса. Реальной утечки не обнаружено и backup на устройстве не проверялся.

`clearData` записывает пустой JSON, а не удаляет файл БД, как утверждает README. Гарантии физического стирания страниц SQLite/WAL отсутствуют.

Исправление: явно выбрать backup/device-transfer policy и правдивые формулировки; определить логическую очистку против удаления файлов, не обещать forensic erase. SQLCipher/биометрия — отдельное решение при необходимости, не обязательная замена текущего механизма.

### A24 · P2 · Документация и остатки прежней реализации расходятся с продуктом — код

`pillo-mini-app-description.md` описывает авторизацию, сервер, Blob, email и web-push, которых здесь нет. README обещает постоянный sidebar на планшете, но код использует NativeTabs без явной реализации собственного sidebar; конкретное поведение iPad следует проверить. Комментарий в notifications обещает название лекарства в body, хотя body нейтрален. В App остались неиспользуемые sidebar/nav/history styles, `SectionHeading` не используется; импорт `sf-symbols-typescript` опирается на транзитивную зависимость. Старые шаблонные PNG не используются ссылками приложения/config.

Исправление: один действующий документ native-продукта, старый документ пометить историческим после согласования его назначения; узкая уборка подтверждённого dead code/ресурсов. Не добавлять сервер ради совпадения с устаревшим описанием.

### A25 · P1 · Проверки зависимостей требуют отдельного устранения и triage — проверка

Онлайн `expo install --check` вернул exit 1 с семью расхождениями, таблица ниже. `npm audit` вернул 23 уязвимых узла dependency graph: 8 high, 15 moderate, 0 critical. Это **не 23 доказанных эксплуатируемых дефекта приложения**: часть относится к CLI/Metro/тестам и транзитивным цепочкам. Отдельно проверить runtime-цепочку Router → query-string → decode-uri-component и входящие ссылки.

Исправление: совместимые обновления SDK 57, затем повторный audit и оценка достижимости каждого оставшегося advisory. Автоматическое `audit fix --force` неприемлемо: отчёт предлагает в том числе откат Expo до 46.0.21 и Router до 5.1.11. Нельзя принимать эти предложения как целевые версии.

### A26 · P2 · Проверки не покрывают риски данных и native release — проверка/пробел

В репозитории один файл с тремя тестами календаря. Нет тестов команд/SQLite/fault injection/форм/notification reconciliation, нет lint-команды и lint-конфига. Нет зафиксированной матрицы native release, обновления установленной базы и минимальных ОС. Отсутствие EAS или CI само по себе не дефект: локальные сборки допустимы.

Исправление: регрессии для A01–A19, доступность и device acceptance, минимальная проверка архитектурных границ и lint. Native-компоненты проверять средствами React Native, а не DOM Testing Library. Не требовать переезда тестов на другой runner до проверки совместимости.

## Что уже сделано правильно

- Предметный календарь отделён от native API, есть детерминированные intake ID и тест идемпотентности.
- SQL-параметры payload связаны через placeholders; динамического пользовательского SQL не найдено.
- Используются локальные календарные компоненты Date вместо преобразования date-only через UTC.
- Текст напоминания не содержит названия/дозы; прикладных сетевых отправок и hardcoded secrets в просмотренных исходниках не найдено. Это не аудит всего поведения SDK в runtime.
- Strict TypeScript и noUncheckedIndexedAccess включены, оба платформенных JS-графа собираются.
- Expo сохраняет возможность точечных Swift/Kotlin-адаптеров. В установленном @expo/ui для glass-кнопок есть fallback на старых iOS; отсутствие ручного version check в приложении не объявляется crash-дефектом.
